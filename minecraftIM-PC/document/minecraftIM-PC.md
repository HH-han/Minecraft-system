需要先澄清一个关键点：**Adrenaline.js 目前没有公开的“企业级”官方架构模板或最佳实践文档**。它是一个非常新的轻量级框架，官方仓库仅提供了基础的 CLI 脚手架和 API 示例。因此，以下架构方案是基于其现有能力（Electron 兼容 API、Node.js 主进程、系统 WebView 渲染进程）以及企业级桌面应用的通用需求，所做的**合理设计与推断**。

### 整体分层架构

建议采用与 Electron 类似的三层结构，但充分利用 Adrenaline.js 的轻量特性：

```
┌─────────────────────────────────────────────────────────────┐
│                   渲染进程 (WebView / 前端)                  │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │  UI 组件层   │  │  状态管理    │  │  IPC 调用封装层      │  │
│  │ (React/Vue) │  │ (Pinia/Zustand)│ │ (类型安全的 Bridge) │  │
│  └─────────────┘  └─────────────┘  └─────────────────────┘  │
└──────────────────────────┬──────────────────────────────────┘
                           │ IPC (异步消息)
┌──────────────────────────▼──────────────────────────────────┐
│                   主进程 (Node.js)                           │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │  窗口管理    │  │  业务服务层  │  │  基础设施层          │  │
│  │ (Window Mgr)│  │ (Services)  │  │ (日志/配置/更新/存储)│  │
│  └─────────────┘  └─────────────┘  └─────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### 关键设计决策

**1. IPC 通信的契约化（最重要）**

Adrenaline.js 提供了类似 `ipcMain` 和 `webContents.send` 的双向通信能力，但企业级项目必须避免通道名散落各处、参数类型混乱。建议在 `shared/constants.ts` 中集中定义所有通道，并在 `renderer/bridge/` 中为每个通道提供类型安全的封装函数。主进程侧在 `ipc/handlers/` 中按领域拆分注册，启动时统一挂载。

**2. 主进程服务层与 IPC 处理器分离**

`services/` 中的逻辑应当是可以独立单元测试的纯 Node.js 模块，不直接依赖 Adrenaline.js 的 API。`ipc/handlers/` 只做参数校验和调用转发，保持轻薄。这样当未来需要替换通信层或增加本地 HTTP 接口时，业务逻辑无需改动。

**3. 前端状态管理与 IPC 的边界**

渲染进程的状态管理（如 Pinia/Zustand）只存储 UI 状态和缓存结果。所有需要主进程能力的数据（文件读写、数据库、系统信息）必须通过 `bridge/` 调用，**不要**在前端直接引入 Node.js 原生模块（即使 Adrenaline.js 允许，也会破坏进程隔离的安全模型）。

**4. 窗口管理的单例化**

`window-factory.ts` 负责管理窗口生命周期，确保主窗口只创建一次，并处理 macOS 上 `window-all-closed` 与 `activate` 的标准行为。多窗口场景（如弹窗、设置窗）也统一从工厂创建，便于统一注入配置和监听器。

### 需要留意的风险与补充

**框架成熟度风险**：Adrenaline.js 的 GitHub 仓库目前相对年轻，企业级项目需要评估其长期维护性。建议在业务上做**可迁移设计**：IPC 封装层和主进程服务层尽量与框架 API 解耦，如果未来需要迁移到 Electron 或 Tauri，替换成本可控。

**缺少内置能力**：Electron 生态中的 `electron-updater`、`electron-log`、`electron-store` 等成熟方案，在 Adrenaline.js 中**不能直接使用**（它们依赖 Electron 的原生模块）。企业级应用需要的自动更新、结构化日志、加密存储、崩溃上报等功能，需要自行实现或寻找 Node.js 原生替代方案，这是架构落地时最大的额外工作量。

**构建与分发**：官方目前仅提供开发 CLI（`adrenaline dev`），生产构建、代码签名、安装包制作（NSIS/dmg/AppImage）需要自行搭建流水线。建议尽早规划 CI/CD 中的打包环节，避免临近发布时才发现缺少工具链支持。
